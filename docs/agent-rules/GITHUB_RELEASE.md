# GitHub 및 배포 작업 지침

이 문서는 Git 원격 작업, GitHub 이슈·PR·병합, Actions와 Pages 배포에 적용한다.

## GitHub 작업 표준

- GitHub 관련 조회·이슈·PR·병합·Actions·Pages 작업은 GitHub CLI를 기본 경로로 사용한다.
- Windows에서는 `C:\Program Files\GitHub CLI\gh.exe`를 직접 호출해 `PATH` 차이로 인한 재시도를 피한다.
- 원격 브랜치 fetch·push 같은 Git 전송은 `git`을 사용하고 GitHub 서비스 기능은 위 `gh.exe`로 처리한다.
- GitHub 작업 시작 시 `gh auth status -h github.com`을 한 번만 확인한다. 인증이 정상이면 같은 작업 흐름에서 반복하지 않는다.
- 인증 실패 시 GitHub 앱이나 인앱 브라우저 쓰기 경로를 순환 시도하지 않는다. 사용자에게 `gh auth login -h github.com` 실행을 요청하고 완료 후 인증을 한 번 재확인한다.
- 브라우저 로그인은 CLI 인증 완료로 간주하지 않는다.
- 현재 연결된 GitHub 앱은 저장소 조회 보조용으로만 취급한다. 이슈·PR 생성 같은 쓰기 작업은 처음부터 인증된 `gh.exe`를 사용한다.

## 승인 범위

- 커밋·푸시·PR·병합·배포는 사용자가 승인한 최종 단계까지만 수행한다.
- 사용자가 `PR까지`, `병합까지` 또는 `배포까지`처럼 최종 단계를 지정하면 그 단계까지 필요한 정상적인 중간 작업을 일괄 승인한 것으로 처리한다.
- 같은 범위의 중간 단계마다 승인을 다시 요청하지 않는다.
- 승인 범위를 크게 벗어나는 변경, 문서 충돌, 다른 사람의 변경 수정 또는 복구하기 어려운 작업은 별도 확인한다.
- 강제 푸시, `git reset --hard`, 대규모 삭제는 사용자의 명시적 요청 없이 수행하지 않는다.

## 게시와 병합

- 코드, UI, 문서, 데이터, 그래픽 등 저장소 변경 작업은 종류와 관계없이 시작 전에 최신 `origin/main` 기준의 목적별 전용 브랜치를 만들거나 해당 작업의 기존 전용 브랜치로 전환한다. 사용자가 명시적으로 같은 브랜치에서 이어서 작업하라고 지시하지 않는 한 현재 체크아웃된 다른 작업 브랜치에 새 작업을 섞지 않는다.
- 최신 `origin/main`에서 목적별 브랜치를 만들고 관련 파일만 명시적으로 스테이징한다.
- 커밋 전 변경 범위와 `git diff --check`를 확인하고 사용자·팀원의 무관한 변경을 포함하지 않는다.
- PR 생성 전 최신 `origin/main`과 충돌 여부를 확인한다. 충돌 시 강제 병합하지 않고 사용자에게 알린다.
- 사용자가 merge commit을 요청한 프로젝트 흐름에서는 squash나 rebase merge 대신 Create a merge commit을 사용한다.
- 병합 후 PR 링크, 병합 방식, 병합 커밋 SHA와 원격 `main` 반영 상태를 보고한다.

## Web·Pages 배포

- Web 내보내기 파일명은 `index.html`로 한다.
- Pages는 최신 소스가 아니라 저장소의 `build/web/` 산출물을 배포하므로 기능 변경 배포 전 Web Release 갱신 여부를 확인한다.
- 배포 워크플로는 병합 SHA 기반의 고유 PCK 파일명을 사용해 기존 브라우저 캐시 재사용을 방지한다.
- 배포를 승인받은 경우 Actions 완료, 배포 HTML의 PCK 참조, 원격 파일 해시와 필요 시 실제 Pages 플레이를 확인한다.
- 병합과 배포를 완료하면 Actions/Pages 상태와 최종 플레이 URL을 함께 보고한다.
- GitHub 및 영상 링크는 심사 종료까지 접근 가능하게 유지한다.
