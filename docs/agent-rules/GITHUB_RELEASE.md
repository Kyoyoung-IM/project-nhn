# GitHub 및 배포 작업 지침

이 문서는 Git 원격 작업, GitHub 이슈·PR·병합, Actions와 Pages 배포에 적용한다.

## GitHub 작업 표준

- 원격 브랜치 fetch·push 같은 Git 전송은 `git`을 사용한다. Git 전송 성공 여부와 GitHub CLI 인증 상태를 별개로 판단하며, CLI 토큰이 무효라는 이유만으로 fetch·rebase·push를 중단하지 않는다.
- 저장소·이슈·PR 조회는 연결된 GitHub 앱을 기본 경로로 사용한다. 이슈·PR 생성·병합 같은 쓰기는 해당 저장소에서 앱 쓰기 권한이 확인된 경우에만 앱을 기본 경로로 사용한다.
- PR 생성은 승인된 저장소·base·head를 정확히 지정하고, merge commit 병합은 `merge` 방식과 확인된 최신 head SHA를 지정한다. 권한 확인만을 위한 시험 쓰기는 하지 않으며 승인된 실제 작업으로만 권한을 확인한다. 실제 쓰기에서 `403 Resource not accessible by integration`이 확인되면 권한 변경이 확인될 때까지 다른 채팅에서 같은 앱 쓰기를 반복하지 않는다.
- GitHub Actions 상세 로그, 실행 제어 또는 GitHub 앱이 지원하지 않는 서비스 작업에만 GitHub CLI를 사용한다. Windows에서는 `C:\Program Files\GitHub CLI\gh.exe`를 직접 호출해 `PATH` 차이로 인한 재시도를 피한다.
- `gh auth status -h github.com`은 작업 시작 시 선제적으로 실행하지 않는다. 남은 승인 범위에 GitHub CLI가 꼭 필요한 단계가 있을 때 그 단계 직전에 한 번만 확인하고, 인증이 정상이면 같은 작업 흐름에서 반복하지 않는다.
- CLI 인증 실패가 발생해도 `git`이나 GitHub 앱으로 수행 가능한 승인 범위는 계속 진행한다. CLI로만 가능한 필수 단계가 실제로 남았을 때만 사용자에게 `gh auth login -h github.com` 실행을 한 번 요청하고, 완료 후 인증을 한 번 재확인한다. 브라우저 승인을 마친 뒤에도 토큰이 무효이면 같은 채팅이나 후속 채팅에서 로그인을 반복 실행하지 않고, 기존 로컬 자격 증명 정리 또는 연결 복구가 한 번 필요한 지속 장애로 보고한다.
- GitHub 앱의 실제 작업이 권한 오류로 실패하면 같은 호출을 반복하지 않는다. 그 작업을 CLI가 지원하고 CLI 인증이 정상이면 한 번 전환하며, 두 경로 모두 사용할 수 없을 때만 실제로 막힌 단계와 필요한 사용자 조치를 보고한다.
- 브라우저 로그인은 CLI 인증 완료로 간주하지 않는다.
- 도구 전환이나 권한 오류는 실제로 발생해 결과 또는 사용자 조치에 영향을 줄 때만 보고한다. 실제 호출 없이 예상한 오류나 이미 알려진 권한 제한을 작업마다 반복하지 않는다.
- 게시 작업의 시작 안내가 필요하면 작업 범위와 목표 단계만 짧게 밝힌다. 정상적인 CLI 사용 경로는 최종 결과에 필요한 링크·브랜치·커밋·검증 정보보다 앞세우지 않는다.

## 승인 범위

- 커밋·푸시·PR·병합·배포는 사용자가 승인한 최종 단계까지만 수행한다.
- 사용자가 `PR까지`, `병합까지` 또는 `배포까지`처럼 최종 단계를 지정하면 그 단계까지 필요한 정상적인 중간 작업을 일괄 승인한 것으로 처리한다.
- 같은 범위의 중간 단계마다 승인을 다시 요청하지 않는다.
- 승인 범위를 크게 벗어나는 변경, 문서 충돌, 다른 사람의 변경 수정 또는 복구하기 어려운 작업은 별도 확인한다.
- 강제 푸시, `git reset --hard`, 대규모 삭제는 사용자의 명시적 요청 없이 수행하지 않는다.

## 게시와 병합

- 코드, UI, 문서, 데이터, 그래픽 등 저장소 변경 작업은 종류와 관계없이 시작 전에 최신 `origin/main` 기준의 목적별 전용 브랜치를 만들거나 해당 작업의 기존 전용 브랜치로 전환한다. 사용자가 명시적으로 같은 브랜치에서 이어서 작업하라고 지시하지 않는 한 현재 체크아웃된 다른 작업 브랜치에 새 작업을 섞지 않는다.
- 최신 `origin/main`에서 목적별 브랜치를 만들고 관련 파일만 명시적으로 스테이징한다.
- 커밋 전에 `build/web/`과 작업용 임시 빌드 위치를 확인해 현재 결과 확인·배포에 쓰지 않는 이전 빌드를 모두 정리한다. 삭제 대상은 먼저 열거하고, 유지할 최신 빌드와 사용자·팀원 파일을 구분한 뒤 삭제한다.
- 커밋 전 변경 범위와 `git diff --check`를 확인하고 사용자·팀원의 무관한 변경을 포함하지 않는다.
- PR 생성 전 최신 `origin/main`과 충돌 여부를 확인한다. 충돌 시 강제 병합하지 않고 사용자에게 알린다.
- 사용자가 merge commit을 요청한 프로젝트 흐름에서는 squash나 rebase merge 대신 Create a merge commit을 사용한다.
- GitHub 앱 쓰기 권한과 CLI 인증이 모두 실제로 실패한 상태에서 사용자가 PR 우회를 명시적으로 승인한 경우에만 예외적으로 최신 `origin/main`에서 로컬 `--no-ff` merge commit을 만든 뒤 Git으로 `main`에 직접 푸시할 수 있다. 직접 병합 전 원격 `main` 갱신, 작업 브랜치 head, 병합 diff와 대상 저장소를 다시 확인하며, 브랜치 보호가 거부하면 우회하지 않는다.
- 병합 후 PR 링크, 병합 방식, 병합 커밋 SHA와 원격 `main` 반영 상태를 보고한다.

## Web·Pages 배포

- Web 내보내기 파일명은 `index.html`로 한다.
- 사용자가 배포를 명령하면 커밋 전에 확인용 임시 로컬 서버를 중지하고 `build/web/`의 임시 플레이 산출물과 현재 배포에 사용하지 않는 구버전 PCK·Web 산출물을 명시적으로 정리한다. 삭제 대상을 먼저 열거한 뒤 최신 소스에서 새 Web Release를 내보내며, 커밋에는 현재 배포에 필요한 최신 산출물만 포함한다.
- Pages는 최신 소스가 아니라 저장소의 `build/web/` 산출물을 배포하므로 기능 변경 배포 전 Web Release 갱신 여부를 확인한다.
- 배포 워크플로는 병합 SHA 기반의 고유 PCK 파일명을 사용해 기존 브라우저 캐시 재사용을 방지한다.
- Pages 워크플로의 자동 배포 대상은 `main`의 `build/web/**` 또는 워크플로 자체 변경으로 제한한다. 문서·현황판만 바뀐 커밋에는 불필요한 Pages 배포를 만들지 않는다.
- Pages 배포는 `github-pages` 동시성 그룹에서 직렬 실행하며 진행 중 실행을 새 실행이 취소하지 않도록 `cancel-in-progress: false`를 유지한다.
- `actions/deploy-pages@v4`의 Pages 상태 대기 제한은 최대 600,000ms(10분)이며 더 늘릴 수 없다. `timeout`에 더 큰 값을 넣어 우회하지 않고 기본 제한을 사용한다.
- 업로드 완료 후 `deployment_queued` 또는 `in_progress`이면 10분 제한까지 기다린다. 제한시간 실패는 Web 빌드 실패와 구분해 Pages 서비스 지연으로 기록하고, 같은 SHA를 즉시 재실행하지 않는다.
- 실패 작업의 `runner_name`이 비어 있고 실행 step이 0개이며 `The job was not acquired by Runner of type hosted even after multiple attempts` 주석이 있으면 Pages 큐 지연이 아니라 GitHub-hosted runner 미할당으로 판정한다. 이 경우 checkout과 아티팩트 업로드가 시작되지 않았으므로 뒤늦은 Pages 게시를 기다리는 대상이 아니다.
- runner 미할당 실패 후 공개 HTML이 직전 PCK를 유지하는 것을 확인했으면 같은 SHA를 재실행하지 않는다. 빈 커밋이나 문서 전용 커밋 대신 실패 실행 ID를 식별할 수 있는 배포 복구 메타데이터처럼 `build/web/**`에 실제 변경을 남긴 새 Web Release SHA를 만들고, 한 실행만 병합·추적한다. 성공 후에는 새 병합 SHA 기반 PCK 이름과 원격 해시를 확인한다.
- Actions가 제한시간 실패로 끝나도 Pages 백엔드가 해당 배포를 뒤늦게 게시할 수 있다. 실패 직후 새 실행을 만들지 말고 배포 객체 상태와 공개 HTML의 PCK 참조를 다시 확인한 뒤 실제 미배포 여부를 판정한다.
- 사용자가 작업 중단을 요청해도 모니터링만 중단하며, 이미 시작된 Actions나 Pages 배포까지 취소하라는 명시적 지시가 없으면 외부 배포는 취소하지 않는다.
- 같은 SHA의 Pages 배포를 취소한 뒤 워크플로만 재실행하면 취소된 Pages 상태를 재사용할 수 있으므로 반복 재실행하지 않는다. 원인을 수정한 실제 커밋으로 새 SHA를 만든 뒤 한 번만 배포한다.
- Pages 지연을 복구하기 위한 빈 커밋이나 현황판 전용 커밋을 만들지 않는다. 먼저 Actions 단계별 상태, `github-pages` 배포 객체, GitHub 공식 Pages 상태를 확인한다.
- 제한시간을 넘긴 배포가 있으면 Actions 실행 취소와 Pages 배포 취소를 별개로 취급한다. 고아 상태가 확인된 특정 Pages 배포만 공식 API로 정리하고, 다른 정상 배포나 저장소 전체 배포 기록은 건드리지 않는다. 공개 PCK 재확인 후에도 실제 미배포이고 Pages가 공식적으로 정상이라면 반복 배포 대신 실행 ID와 배포 ID를 기록해 GitHub Support에 문의한다.
- 여러 작업 채팅에서 병합·배포가 필요하면 한 작업만 배포 완료 확인을 담당한다. 다른 작업은 진행 중 배포가 끝난 뒤 병합해 새 배포를 시작한다.
- 현재 Web 게임은 서버 세션이나 멀티플레이 연결이 없는 정적 빌드다. 이미 로드된 브라우저 세션은 배포 교체나 실패의 영향을 받지 않고 계속 실행되며, 새 접속이나 새로고침만 당시 게시된 버전을 받는다.
- Pages 배포가 실패하면 직전 성공 버전이 계속 제공된다. 배포 실패를 서비스 중단으로 표현하지 말고 공개 HTML의 PCK 참조로 실제 게시 버전을 확인한다.
- 배포를 승인받은 경우 Actions 완료, 배포 HTML의 PCK 참조, 원격 파일 해시와 필요 시 실제 Pages 플레이를 확인한다.
- 병합과 배포를 완료하면 Actions/Pages 상태와 최종 플레이 URL을 함께 보고한다.
- GitHub 및 영상 링크는 심사 종료까지 접근 가능하게 유지한다.
