# UI 작업 지침

이 문서는 UI 배치·구성·스타일·상호작용과 UI 변경의 Web 검증에 적용한다.

## 작업과 승인

- UI의 위치를 옮기거나 구성 요소를 추가·삭제·통합·분리하기 전에는 매우 간단한 예상 배치도를 사용자에게 먼저 제시한다.
- 사용자가 예상 배치도를 승인하기 전에는 해당 UI 배치·구성 변경을 구현하거나 Web 빌드에 반영하지 않는다.
- 색상·폰트·테두리처럼 위치와 구성에 영향을 주지 않는 순수 스타일 변경은 배치 승인 대상에서 제외한다.
- 승인된 배치도 범위 안의 구현과 관련 UI 테스트는 다시 승인받지 않는다.
- 새 비트맵 에셋 제작은 UI 작업에 자동 포함되지 않는다. `IMAGE_GENERATION.md`의 허용 기준을 함께 적용한다.
- 화면, 조작 또는 게임 규칙이 바뀌면 `DESIGN.md`와 `docs/GAME_SPEC.md`의 관련 항목을 함께 갱신한다.

## 구현과 검증

- 변경 전 관련 장면과 스크립트를 읽고 기존 사용자 작업을 확인한다.
- 정적 위치·크기·폰트·색·스타일은 가능한 한 Godot 씬과 Inspector에서 편집 가능하게 유지하고, 런타임 스크립트는 데이터·입력·상태 갱신을 담당한다.
- 변경된 UI의 정상 상태, 대표 실패 상태와 조작 종료 후 복원 상태를 관련 전용 테스트로 확인한다.
- 관련 없는 전투·데이터·전체 회귀 테스트는 UI 변경에 필요하지 않으면 실행하지 않는다.

## UI 변경 Web 배포 완료 체크리스트

- 사용자가 Web 검증을 명시적으로 생략하지 않았다면 아래 순서를 한 작업 흐름에서 확인한다.
  1. 변경된 UI의 Godot 장면 파싱과 관련 전용 테스트를 통과한다.
  2. 최신 소스로 Web Release를 다시 내보내 `build/web/index.html`과 `build/web/index.pck` 등 실제 배포 산출물이 갱신됐는지 확인한다.
  3. 임시 로컬 HTTP 서버에서 초기 상태, 변경 상태와 복원 상태를 실제 Web 화면으로 확인하고 콘솔 오류·경고를 점검한다.
  4. 소스와 필요한 Web 산출물을 같은 배포 범위에 포함한다. 병합 전에 발견한 문제는 같은 브랜치와 PR에서 수정해 소스 PR, 빌드 PR, 캐시 PR로 불필요하게 분리하지 않는다.
  5. Pages 워크플로가 병합 커밋 SHA 기반의 고유 PCK 파일명을 생성하고 배포 HTML이 그 파일을 요청하는지 확인한다.
  6. 배포 완료 후 원격 PCK와 검증한 로컬 Web Release의 SHA-256 해시가 일치하는지 확인한다.
  7. 사용자가 배포 후 실제 Pages 플레이 검증을 명시적으로 생략하지 않았다면 캐시 무효화 URL에서 변경 화면과 Web 콘솔을 최종 확인한다.
- 커밋·푸시·PR·병합·배포는 `GITHUB_RELEASE.md`의 승인 범위와 절차를 따른다.
